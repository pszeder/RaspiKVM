RaspiKVM: build and deploy on the spare Pi

The project is now named RaspiKVM. Existing checkout paths such as D:\source\RaspiKey, runtime names and local key filenames below are retained intentionally; substitute your own checkout path. The current feature branch is dev/modern-kvm.

Everyday development

Set-Location D:\source\RaspiKey
.\dev.ps1 doctor     # Check identity, permission, services, Bluetooth and USB internet
.\dev.ps1 update     # Build, upload, compile changed native objects, activate
.\dev.ps1 rollback   # Restore the previous release
.\dev.ps1 logs       # Read the service journal
.\dev.ps1 ssh        # Open an SSH shell
.\dev.ps1 reboot     # Reboot only the configured spare
.\dev.ps1 poweroff   # Shut down the spare before unplugging

build creates a bundle without deployment; deploy -Bundle PATH installs a selected bundle; restart restarts the application. Routine code/UI updates and rollback authenticate with the SSH key, with no sudo prompt. Updates briefly interrupt the spare's keyboard input while its application restarts; they preserve settings, pairing and USB networking. Open the spare control UI.

The ignored .dev/settings.json stores the Pi UUID, pinned SSH host key, USB MACs and default address. Commands discover its USB DHCP address when possible and verify host key/UUID before changes. If DHCP changes and automatic discovery is ambiguous, pass -Target NEW_IP; the pinned identity checks still apply. The dedicated key is D:\source\RaspiKey\.dev\ssh\id_ed25519, readable only by your Windows account; the adjacent .pub file is the public key for Imager. This local directory is excluded from Git, WSL source copying and deployment bundles. Keep it on this PC.

The target is your Pi Zero W 1.1. Build, installation and fast updates are one milestone. Keep the working keyboard Pi connected and unchanged; do not pair its A1314 with the spare during setup.

2. Enable USB networking before first boot

Run this in PowerShell, replacing E: with the spare card's boot partition:

powershell -NoProfile -ExecutionPolicy Bypass -File "D:\source\RaspiKey\scripts\development\Prepare-DevSD.ps1" -BootDrive E:

The helper edits cloud-init, preserves user/key settings and saves a backup on that card. It does not format a disk. It refuses unexpected filesystems or credentials. If it reports missing user-data or an unexpected username/hostname, use a current Imager and Trixie image and check the customization settings.

Eject the card, insert it into the spare Pi, and connect a data-capable micro-USB cable to the port labelled USB, closest to HDMI. The PWR IN port carries no data. Allow several minutes for first boot and any automatic reboot. This spare needed a second boot before USB appeared. If no new USB device appears after about ten minutes, let activity settle, then power-cycle only the spare.

3. Identify the spare adapter and share internet

Get-NetAdapter | Format-Table ifIndex, Name, InterfaceDescription, MacAddress, Status

Compare the adapter list before/after connecting the spare. Leave the original 169.254.1.1 Pi's adapter unchanged. If the new USB Ethernet device is unrecognized, install the official Raspberry Pi USB RNDIS driver. See the official USB network instructions.

  1. Run ncpa.cpl.
  2. Open Properties for the Windows connection providing your internet/LAN access.
  3. On Sharing, enable “Allow other network users to connect…” and choose the new spare Pi adapter.
  4. Allow approximately a minute for DHCP and the Pi's networking watcher to switch into client mode.

Windows commonly uses 192.168.137.1 on the shared host adapter; the Pi receives another address on that subnet. Without ICS, the OS's standalone USB network uses Pi address 10.12.194.1. Neither uses the original Pi's address.

After the composite-gadget reboot, Windows briefly reported an unrecognized USB device, then successfully enumerated networking, keyboard and consumer-control interfaces with no device errors. Check the current device state before reinstalling drivers or changing the SD card. If ICS retains the vanished initial adapter and its API reports 0x80040201, reselect the development adapter in the upstream connection's Sharing tab. On this PC, the upstream is vEthernet (New Virtual Switch); select Ethernet 6.

Network access through USB depends on the PC being awake, connected and sharing its connection. This includes future Home Assistant access. VPN or subnet overlap issues will be diagnosed on the spare link without resetting unrelated adapters.

5. Build and install

The frontend builds in WSL's Linux filesystem with verified Node 22.13.1 and a pinned npm lockfile. The backend builds natively with the Pi's own compiler/libraries. This avoids ARM cross-toolchain mismatches and installing Node on the Zero W. Native objects are cached for incremental updates.

WSL Ubuntu dependencies are installed on this PC. On another machine, install git, rsync, curl, xz-utils and ca-certificates first.

powershell -NoProfile -ExecutionPolicy Bypass -File "D:\source\RaspiKey\scripts\development\Build-DevBundle.ps1"

The bundle and checksum appear under D:\source\RaspiKey\dist. A verified source + built-UI bundle is already available locally in D:\source\RaspiKey\dist. It includes no personal keys or precompiled ARM binary.

$bundle = Get-ChildItem "D:\source\RaspiKey\dist\raspikey-dev-*.tar.gz" | Where-Object Name -NotMatch 'fault-test' | Sort-Object LastWriteTime -Descending | Select-Object -First 1
& "D:\source\RaspiKey\scripts\development\Deploy-DevBundle.ps1" -Target raspikey-dev.local -IdentityFile $key -Bundle $bundle.FullName -InteractiveSudo

The installer verifies hostname, board, architecture and OS. Its first native compile is slow on the original Zero W: it uses one compiler job and temporary swap if needed. It records compiler/library versions and checks the executable's ARMv6 attributes.

After the first installation, run sudo reboot once. The Pi will expose USB networking plus the original keyboard HID interface. Windows may create a new composite-device adapter; reassign ICS to that new development adapter. The original Pi remains unchanged.

The modern service enables only the Bluetooth radio before starting RaspiKey. Fresh Trixie can leave that radio soft-blocked. Wi-Fi stays disabled; USB provides networking.

systemctl status raspikey-dev-usb.service raspikey-dev.service
curl http://127.0.0.1/info
journalctl -u raspikey-dev.service -n 60 --no-pager

Open http://raspikey-dev.local/, or use the development Pi's IP. Test keyboard behavior using a spare keyboard or a planned A1314 handover.

6. Updates and rollback

Run .\dev.ps1 update in the configured checkout. Updates install a versioned release, restart only RaspiKVM, check its expected HTTP release identity, and restore the previous release and service configuration on activation failure. The native build runs as raspidev, retains object-file caches and skips temporary swap when native source is unchanged. Manual rollback is password-free:

.\dev.ps1 rollback

Application settings persist in /var/lib/raspikey; Bluetooth uses its normal BlueZ state directory. Updates preserve both. USB descriptors, kernel and Bluetooth-stack changes are separate maintenance work. Ordinary application updates do not reflash the SD card or recreate USB networking.

The development OS is writable: use .\dev.ps1 poweroff before unplugging it. Everyday-use read-only storage and a complete generated image remain later milestones.

7. Deployment permissions and maintenance

The installed root-owned command is /usr/local/libexec/raspikey/deploy-control.sh. A visudo-validated rule in /etc/sudoers.d/raspikey-dev-deploy permits raspidev to invoke that fixed entry point without a password. It checks the Pi/account identity, limits operations, snapshots uploads into a private root directory, verifies archive/manifest checksums, rejects links/path escapes, and serializes changes. Application configuration continues through the web UI and persistent state directory.

Normal deployment uses the installed privileged framework. Uploaded shell helpers and systemd units are not executed or substituted. The developer's application code compiles as raspidev; the resulting program runs with the privileges needed by the current HID/BlueZ implementation. Changes to deployment tools, system services, USB gadget or OS packages are maintenance work and use the explicit setup workflow with its occasional sudo prompt:

.\dev.ps1 build
.\dev.ps1 setup

A warning about differing privileged tooling means the application deployed using the already installed framework; use setup when intending to update that framework. The interactive path is also used once on a freshly flashed card. After that card exposes the composite gadget, configure its local profile using the verified SSH key/known-hosts file and its identified host-adapter MAC:

& .\scripts\development\Configure-DevHost.ps1 -Target PI_ADDRESS -IdentityFile KEY_PATH -KnownHostsFile VERIFIED_HOSTS_PATH -HostMac HOST_ADAPTER_MAC
.\dev.ps1 doctor

The profile is tied to this spare; a replacement Pi needs its own verified profile. Do not commit or publish .dev.

Native debugging and tests

The Pi's incremental source/build caches are /var/cache/raspikey-build/source and /var/cache/raspikey-build/build, owned by raspidev. Compiler/package versions and binary hashes are captured in each release's build-info.txt. The active release is /opt/raspikey/current; retained releases allow rollback. C++ changes build on the Pi; UI changes build in WSL. Initial compilation can take many minutes on a Zero W; later builds compile only changed objects. Restore a good bundle with .\dev.ps1 deploy after a failed experiment.

wsl -d Ubuntu -- bash -lc 'python3 /mnt/d/source/RaspiKey/tests/development/test_upload.py'
wsl -d Ubuntu -- bash -lc 'g++ -std=c++14 -pthread /mnt/d/source/RaspiKey/tests/development/test_async_value_cache.cpp -o /tmp/raspikey-cache-test && /tmp/raspikey-cache-test'

On the modern runtime, Bluetooth battery reads run in a background cache refreshed at most once per minute. A slow keyboard/kernel response cannot block the web UI; the latest valid value is retained and initially unavailable values are omitted. The original legacy runtime path is preserved.

Validation boundary

Verified on the spare: native ARMv6 build with Trixie GCC 14.2/Boost 1.83; service startup after reboot; USB network/keyboard/consumer-control enumeration; SSH and web/API access; DNS and HTTPS through Windows ICS on the final Ethernet 6 adapter; Bluetooth power-on; incremental native update, manual rollback and restoration of the latest release. The unchanged native source reported ninja: no work to do on both update passes. The user confirmed successful typing through a spare A1314. BlueZ reports that keyboard paired, trusted and connected; its Linux devices are event2 and hidraw0, vendor/product 05AC:0256. The original keyboard Pi has not been modified.

SSH-key-only update, rollback and restoration passed after clearing sudo's credential cache; ordinary sudo still required a password. An intentionally failing application was rejected and the previous release automatically restored, then a good deployment cleared the failed build from the native cache. Reboot restored the same USB adapter identity, DHCP address, SSH access and outbound HTTPS without changing Windows sharing. The A1314 pairing/trust remained saved; press a key to wake/reconnect it after reboot. Windows PowerShell 5.1 and PowerShell 7 run the doctor command. Archive tests cover traversal, checksum failures, links, duplicate/uncovered files, private-directory checks and ownership. A blocking fake battery reader verified responsive cached reads and single-query behavior; the real device API responded in about 60 ms after the fix. Exhaustive modifier/media-key behavior remains a later functional test. A full generated disk image remains optional; the supported setup path is a stock Trixie Lite image plus these scripts.
