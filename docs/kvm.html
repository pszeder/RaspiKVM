RaspiKVM: USB and Bluetooth input switching

The spare Pi receives the A1314 and MX Master 3S and sends their input to one selected computer: the USB-connected Windows PC or a Bluetooth computer such as a Mac. The KVM routes input; optional TV control also selects the corresponding HDMI source. USB networking and the web UI remain available through the Windows PC. The production Pi at 169.254.1.1 is unchanged.

Pair the Mac

  1. Keep the spare connected to Windows over USB, with the spare keyboard and the mouse's development slot connected to RaspiKey.
  2. Refresh the spare Pi's web UI. In Host switching, check Enable Bluetooth output and click Save host settings.
  3. Click Open pairing for 2 minutes. On the Mac, open System Settings → Bluetooth and connect to RaspiKey KVM. The Pi initiates the Bluetooth bond automatically when the Mac connects; no terminal command is needed. Pair the Pi with the Mac; keep the keyboard and mouse paired with the Pi.
  4. If macOS shows Keyboard Setup Assistant, follow its prompts to identify the keyboard. Select the matching input language in macOS; RaspiKVM sends key codes, not translated characters.
  5. Wait for Ready to receive input. Use the web button or the configured shortcut to switch both devices.

Switch hosts

The initial shortcut is Ctrl+Alt+F12. Hold those modifiers and press F12, then release all keys. You can configure Ctrl, Alt, Shift and/or Win/Cmd with F1–F12, a letter, Space or Tab. At least Ctrl, Alt or Win/Cmd is required. Left and right modifier keys both work. The switch key itself is consumed rather than sent to either host; modifier presses before the chord can reach the old host and are released when switching.

The shortcut is evaluated after the existing Apple filter and custom keymap. Fn/Control stay as labeled. The two-key international keymap copied from the working Pi remains installed. The Windows/Command key is reported as the host's standard GUI modifier, so it is Windows on the PC and Command on the Mac.

Switching releases keys, mouse buttons and consumer controls on the old host, then suppresses input until every physically held key/button is released. This prevents a held switch chord or drag from appearing on the new host. Pointer movement and both wheels then follow the selected host. The mouse's configurable button shortcuts are forwarded as keyboard input on that host. Button mappings are currently shared between hosts; an operating system may assign different actions to the same shortcut.

A Bluetooth output disconnect returns input to USB. If the paired host is disconnected, choosing Bluetooth opens a 60-second connection window while USB continues receiving input. Once the host reconnects and subscribes to keyboard and mouse reports, RaspiKVM switches to it and requests wake. Press the switch shortcut again or click Use USB computer to cancel the pending switch. If the host does not become ready, routing stays on USB. Reconnection advertising accepts only the saved output host; it does not open pairing for nearby computers. The already bonded host is marked trusted in BlueZ, and HID input reports require an encrypted Bluetooth link. Forget output host returns to USB and removes only the selected computer's Bluetooth bond, allowing you to pair another output host.

Mac sleep and wake

When the Mac reports HID Suspend, input returns to USB automatically. Duplicate sleep notifications do not cause extra switches. Pending Bluetooth movement is discarded and ordinary input goes to Windows. Keyboard/mouse cleanup while USB is selected also sends no Bluetooth input reports.

A connected, sleeping Mac remains selectable. Press Ctrl+Alt+F12 on the spare keyboard or click Use Bluetooth computer to select it. RaspiKVM advertises RemoteWake support and sends a single bare Shift press/release to request wake, without typing a character or clicking an application. It clears its saved sleep hint on this explicit request even if macOS never sends Exit Suspend. Releasing the switch chord is still required before normal input resumes. A queued wake is discarded if the user cancels, disables output or the application stops before it is delivered. External wake does not automatically steal input from Windows.

Updates and restarts start on USB, preserve bonds and settings, and wait for an explicit pairing action or switch before advertising Bluetooth output. During orderly shutdown, RaspiKVM stops advertising and disconnects the Mac before removing its GATT application. This addresses service rediscovery during updates as well as unsolicited cleanup reports. The next explicit switch reopens advertising for the saved host. Startup and routine PC input do not request Mac wake.

The wake request requires a usable Bluetooth HID connection; a disconnected Mac must reconnect during the explicit connection window before the Shift tap can be sent. A sleeping Mac that does not scan/reconnect cannot be woken by this path. The Sleep reported message is based on the Mac's HID notification, not a measurement of its display or power state. macOS decides whether to accept Bluetooth wake. If wake fails because macOS cached an older HID capability, re-pair the output host; source keyboard and mouse pairing is retained. Hardware observation is required to confirm whether a particular Mac sleep mode remains quiet through an update and accepts the wake request.

Consistent scrolling on the Mac

Reverse scrolling on Bluetooth computer is enabled for this Mac setup. It reverses the vertical wheel and horizontal thumb wheel only while the Bluetooth host receives input, compensating for macOS Natural scrolling. USB wheel direction, pointer movement and buttons are unchanged. The setting is saved with the host settings; disable it if Natural scrolling is turned off on the Mac or you pair a Bluetooth computer that does not need reversal.

Implementation and recovery

Bluetooth output uses the standard HID over GATT profile through BlueZ. A separate GIO main-loop thread exports the HID report map, keyboard, mouse and consumer reports, boot reports, keyboard LED output and device information. The Pi's existing Bluetooth central role for the mouse and Classic connection to the keyboard remain active. No Logitech program or receiver is required on the output computer.

The report router serializes switching with input forwarding. USB input writes remain direct; Bluetooth reports wake their worker through eventfd rather than waiting for a periodic timer. Keyboard reports from the physical keyboard and mouse shortcuts are combined for Bluetooth, with duplicate keys removed and standard six-key rollover behavior. Bounded queue overflow releases Bluetooth state and returns routing to USB. Bluetooth's negotiated radio interval and the shared controller still affect total latency; this version has no measured end-to-end latency guarantee.

Only one Bluetooth output computer is supported. New host pairing is permitted during the explicit two-minute window; subsequent access is pinned to the saved host address. The pairing agent continues authorizing HID reconnects from already trusted input keyboards/mice. The settings file is /var/lib/raspikey/kvm.json. Active routing is deliberately not persisted.

Application rollback closes the Bluetooth output connection and returns the USB bridge to its previous behavior. It preserves the keyboard keymap and mouse settings. Daily app deployment uses the existing SSH key and requires no new sudo rule or password. This feature does not change USB descriptors or require an SD-card write.

Protocol references: BlueZ GATT API, BlueZ advertising API, and BlueZ pairing-agent API.

Sleep/wake regression tests exercise the actual router with anonymous USB pipes and the real Bluetooth transport on a private D-Bus. They verify automatic USB fallback, release/quarantine of held input, duplicate sleep hints, shortcut and API selection, queue failure recovery and the usual connection/bond/subscription/protocol guards. Tests also cover quiet USB cleanup, pending-switch cancellation, reconnect before wake, connection timeout and cancellation of queued wake. The notification test verifies the RemoteWake flag, suppression of ordinary sleeping-host input and exactly one Shift press followed by release. Desktop and mobile web checks cover selection of sleeping and disconnected paired hosts, and cancellation through the USB button. Physical quiet-update behavior and Mac wake acceptance need the hardware test; successful queueing is not proof that the Mac woke.
