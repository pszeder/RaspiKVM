RaspiKey: direct LG TV control

The spare Pi controls the LG 55NANO966PA directly through its local webOS interface. HDMI 4 belongs to the USB Windows PC; HDMI 3 belongs to the Bluetooth Mac. Source selection uses fixed input IDs, so a failed request or an unrelated TV input cannot reverse the mapping. The production Pi is unchanged.

Setup

Network discovery found the TV at 192.168.1.192, using Wi-Fi MAC C8:99:B2:A0:3C:B8. The advertised wired MAC is 7C:64:6C:21:E4:0A; use that instead if the TV moves to Ethernet. The Pi can reach the TV's TLS control port through Windows USB Internet sharing. Wake-on-LAN is already configured on the TV and works from Home Assistant.

  1. Refresh the spare web UI and find TV control.
  2. Enable direct LG TV control. Enter the TV address and active network MAC. Keep USB / PC at HDMI 4 and Bluetooth / Mac at HDMI 3. Save TV settings.
  3. Click Pair TV, then accept the connection prompt on the TV with its remote. Pairing is independent of the existing Home Assistant connection.
  4. Show current computer selects the TV input matching the current KVM route. The existing switch shortcut also changes the TV input after the Bluetooth host is ready; a failed Mac connection leaves PC routing and HDMI 4 selected.
  5. Enable wake from keyboard/buttons/scrolling, and optionally mouse movement. Wake TV is an explicit manual test.

The TV address may change with DHCP. A reservation in the router, or updating this setting when needed, keeps direct control working.

Wake behavior

Actual key presses, mouse buttons, scrolling or enabled mouse movement request wake when the TV is unavailable, in standby or has its screen off. Releases and empty input reports do not count as activity. Movement must accumulate at least eight motion units during a 100 ms worker interval to reject tiny isolated jitter. Wake requests are limited to one every ten seconds. The TV's reported power state is cached through its subscription; normal input on an active TV produces no wake traffic.

App startup, saving settings and automatic fallback from a sleeping/disconnected Mac do not send Wake-on-LAN. Explicit switching and manual wake are user intent. When waking completes, the selected host's fixed HDMI source is applied. TV failures do not change keyboard/mouse routing. RaspiKey never sends TV power-off commands.

The optional additional wake address can be the TV LAN's broadcast address, 192.168.1.255 in this setup. Each wake sends the magic packet to the TV address and this configured additional destination. USB Internet sharing crosses a subnet, so direct TV control working does not prove that wake broadcasts arrive. If both unicast and directed broadcast are blocked, use a wake relay on the TV LAN, such as the existing Home Assistant automation; no TV reconfiguration is necessary.

Performance and development

The input-forwarding path only inspects the report type and sets atomic activity flags/counters. It does not perform network calls, JSON work, disk I/O or take the TV control mutex. A dispatcher coalesces activity at 100 ms intervals and sends small control messages to a separate Python process running at nice 10. The worker owns TV connections, TLS, pairing, subscriptions, source changes and wake packets. It receives host/activity intent, never typed characters or raw mouse reports. This design bounds the input-path work; it is not an end-to-end latency measurement.

The Python worker and pinned Apache-2.0 websocket-client 1.9.0 wheel are embedded in the native executable. They load through anonymous memory files, so regular key-only app deployment needs no new package installation, sudo permission, systemd service, USB descriptor update or SD-card write. CMake generates a separate worker resource from raspikey/tv/worker.py and verifies the wheel SHA256 before compiling. Python-only edits rebuild this small resource instead of the native controller. Tests cover settings validation, report/activity filtering, actual embedded worker startup/IPC, magic packets, explicit versus automatic wake, fixed HDMI selection, pairing/reconnect behavior and command coalescing.

TV settings are stored in /var/lib/raspikey/tv.json; the paired client key and approved TV TLS certificate fingerprint are in /var/lib/raspikey/tv-secret.json, mode 0600. The key is never returned by the settings API. Reconnection checks the saved certificate before sending the client key. A changed certificate requires explicit re-pairing. Forget TV pairing removes only RaspiKey's local TV credentials, not Home Assistant's connection.
